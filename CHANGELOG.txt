2026-09-19  修复：快速滚动时 CPU 进度条与进程列表"鬼畜"
--------------------------------------------------------------------------------

【问题】

对终端做快速的触控板两指滑动时，CPU 占用进度条和进程列表会剧烈跳动、来回
洗牌。这不是渲染问题，是算出来的数值本身疯了。


【根因】

1) 主循环的节拍由输入决定，而不是由定时器决定（主因）

   main.c 的循环体是「采样 -> 标脏 -> 绘制 -> ui_wait(interval)」，而
   ui_wait() 内部的 getch() 对一个**已经缓冲好**的按键会立刻返回——timeout()
   只限制"等不到键"时等多久。

   一次两指滑动会灌进来几十上百个方向键序列，于是循环周期从 1000ms 塌缩到
   约 8ms。而 sysinfo_cpu() 和 proclist_sample() 报告的**都是速率**，量的是
   两次调用之间的间隔——这条契约写在 proclist.h 的注释里，却没有任何代码
   守着它。

   后果：
     - CPU tick 是 10ms 一个，8ms 的窗口在 4 核机器上只剩个位数个 tick，
       busy% 只能落在少数几个离散值上。实测 1.2ms 间隔下取值集合就是
       {0, 33.3, 50, 100}。
     - 进程占用变成"这几毫秒里谁被调度过"的随机数，再拿它 qsort，等于每帧
       把整张表重新洗一遍。
     - "CPU 60s" 火花线每轮循环推一个采样，60 格在 0.6 秒内填满并开始滚动，
       而不是 60 秒。
     - 每个循环还重跑一遍全部采样：proclist_sample 4.4ms（几百个 PID 各一次
       proc_pidinfo 和 proc_name）、smc_fans 3.6ms，约 110 次/秒 = 自造
       ~70% 的一个核。而 macmon 又在测自己的宿主，这笔开销被算回它自己的
       读数里，形成正反馈。

2) 每个滚动事件整屏重写一次

   滚动类按键会置上 repaint_all，下一帧就 erase() + redrawwin() 整屏重写。
   按事件来算就是上百帧、接近 200KB/s，终端画不赢，画面反而更花。

3) 普通模式方向键不在 terminfo 里，尾字节泄漏进了按键 switch

   \E[A 这类序列（正是滚轮发出的）ncurses 不认得，于是退回一个裸 ESC，再把
   剩余字节当成用户手打的字符逐个交出来。其中 \E[C——横向两指滑动发出的
   就是它——以 'C' 结尾，而 'C' 正好是"按 CPU 排序"的快捷键。于是一次斜向
   滑动就能把进程列表的排序在读者眼皮底下翻掉。同时每个滚动事件还因此变成
   三次循环迭代。


【改动】

src/main.c
  - 采样改为由单调时钟的截止时刻驱动，输入只决定何时重绘。截止时刻从上一个
    截止时刻递推（不被采样耗时带偏），错过的直接跳过而不补跑（补跑会连着
    触发采样）。
  - 新增输入排空：一次取走所有已排队的按键（上限 DRAIN_MAX，防自动重复饿死
    重绘），由一帧回应整串。repaint_all 是粘滞标志，一串滚动只花一次重绘。
  - 新增 20fps 帧率上限（MIN_FRAME_SECS）。
  - ui_wait 的超时封顶 250ms，把未识别转义序列造成的卡顿从最长 5s 压到 250ms。
  - 改间隔后新间隔立刻生效，而不是等旧间隔走完剩下的部分。
  - 补上 KEY_RESIZE：暂停时改窗口大小，旧画面原本会错着停留最多 15 秒。
  - 注释全部改为中文。

src/sysinfo.c
  - 新增 MIN_TICKS 下限：tick 总数不足 8 个时沿用上一次读数，并且**不推进
    基线**，让下一次量的窗口自己变宽。

src/proclist.c
  - 新增 MIN_ELAPSED_NS（100ms）下限：窗口太短时沿用上一次的速率、同样不推进
    基线。报一个陈旧的速率，好过报一个由噪声算出来的速率。

src/ui.c
  - ui_init() 用 define_key() 把 \E[A .. \E[D 注册为 KEY_UP/DOWN/RIGHT/LEFT，
    一次解决尾字节泄漏和每个事件三次迭代两个问题。
  - "CPU 60s" 标签改为按实际跨度计算（CPU_HISTORY x interval）：采样修好之后，
    间隔调到 2.25s 时这 60 格其实是 135 秒，写死的标签会说谎。
  - 注释全部改为中文。

src/*.h, Makefile
  - 注释全部改为中文。

README.md
  - 同步：速率契约如何被代码守住、滚动那节的"两件事"扩为"三件事"、
    新增一条关于进程采样开销的待办。


【实测】

同一台机器（macOS 12.7.6，4 核），同一个 200 键突发：

  指标                        修复前        修复后
  -------------------------------------------------------
  采样次数（7.7s 窗口）       603           6
  采样间隔中位数              8.14 ms       1000.86 ms
  间隔 < 250ms 的次数         599 / 602     0
  busy% 相邻跳变 > 40 个点    107           0
  busy% 取值范围              0.0-100.0     31.0-37.3
  突发后 5 秒输出字节         924,780       15,408
  按键解码 \E[A .. \E[D]      27 '[' 'C'    261 KEY_RIGHT

  历史标签（间隔 2.25s）：     "CPU 60s"     "CPU 135s"

其它验证：
  - 从零 make，-Wall -Wextra 零警告
  - 无输入时的基线节奏与原版一致（约 1s 一次），无回归
  - ASan + UBSan：突发、\E[M、裸 ESC、被拆成两半的转义序列、暂停、改排序、
    改间隔、改窗口大小，零报告
  - 带修饰键的方向键（\E[1;2A、\E[1;5C 等）在修复前后返回完全相同的按键，
    说明 define_key 只影响了 \E[A .. \E[D] 这一组，没有波及别的序列


【明确没做的】

进程采样的开销：单次约 4.4ms，几百个 PID 各一次 proc_pidinfo 加一次
proc_name，另外 cached_cpu_ns() 对每个 PID 线性扫一遍 cached[]，整体是 O(n²)。
按 PID 排序后二分、并把进程名缓存起来都能削掉大半——但采样现在每秒才跑一次，
4.4ms 折算下来是 0.44% 的一个核，不值得为此引入新的复杂度。等哪天采样频率
提上去了再回来做这笔账。详见 README 的"可以继续做的"。
